2. Real-World Life Example: The Student Dilemma & FocusFlow Solution

The Problem Scenario (Without FocusFlow)

Meet Rahul, a 3rd-year Computer Science student preparing for upcoming semester examinations. Today, Rahul has exactly 3.0 hours (180 minutes) available to study.

Here is Rahul's current academic status:

  • Subject 1: Data Structures & Algorithms (DSA) — Exam Date: in 4 days | Importance: HIGH
    • Topic A: Binary Search Trees (Estimated: 90 mins, Difficulty: HARD)
    • Topic B: Graph Traversals (BFS/DFS) (Estimated: 120 mins, Difficulty: HARD)
  • Subject 2: Operating Systems (OS) — Exam Date: in 10 days | Importance: MEDIUM
    • Topic C: CPU Scheduling Algorithms (Estimated: 60 mins, Difficulty: MEDIUM)
    • Topic D: Deadlock Prevention (Estimated: 45 mins, Difficulty: MEDIUM)
  • Subject 3: Database Management Systems (DBMS) — Exam Date: in 22 days | Importance: LOW
    • Topic E: SQL Joins & Indexing (Estimated: 45 mins, Difficulty: EASY)

The Human Flaw in Traditional Study Planning:

  1. Analysis Paralysis: Rahul spends 30 to 45 minutes simply deciding where to start or switching frantically between books.
  2. The Comfort-Zone Trap (Procrastination): Because DBMS is easy and SQL Joins feel comfortable, Rahul starts studying SQL Joins for 2 hours. He feels "busy", but has completely ignored his high-priority DSA exam occurring in just 4 days.
  3. Burnout & Panic: By the time the DSA exam arrives, Rahul has not finished Binary Trees or Graphs, leading to cramming, stress, and poor academic performance.

The FocusFlow Solution (With Mathematical Precision)

Rahul inputs his target date (Today) and available study capacity (3.0 hours = 180 minutes) into FocusFlow. The system applies its rule-based Weighted Greedy Scheduling Algorithm.

Priority Score = (Urgency Score × 3) + (Importance Score × 2) + Difficulty Score

Where scoring weights are mapped deterministically:

  • Urgency Score (Days to exam): ≤3 days = 10 pts | ≤7 days = 7 pts | ≤14 days = 5 pts | ≤30 days = 3 pts | >30 days = 1 pt.
  • Importance Score: HIGH = 3 pts | MEDIUM = 2 pts | LOW = 1 pt.
  • Difficulty Score: HARD = 3 pts | MEDIUM = 2 pts | EASY = 1 pt.

Step-by-Step Priority Score Calculation:

Topic Name Subject Days to Exam Urgency Importance Difficulty Calculation Breakdown Final Priority Score
Binary Search Trees DSA 4 days 7 pts 3 pts (HIGH) 3 pts (HARD) (7 × 3) + (3 × 2) + 3 30.0 pts (Rank 1)
Graph Traversals DSA 4 days 7 pts 3 pts (HIGH) 3 pts (HARD) (7 × 3) + (3 × 2) + 3 30.0 pts (Rank 2)
CPU Scheduling OS 10 days 5 pts 2 pts (MED) 2 pts (MED) (5 × 3) + (2 × 2) + 2 21.0 pts (Rank 3)
Deadlock Prevention OS 10 days 5 pts 2 pts (MED) 2 pts (MED) (5 × 3) + (2 × 2) + 2 21.0 pts (Rank 4)
SQL Joins DBMS 22 days 3 pts 1 pt (LOW) 1 pt (EASY) (3 × 3) + (1 × 2) + 1 12.0 pts (Rank 5)

Greedy Time Allocation & Topic Splitting:

  1. Total Daily Capacity: 180 minutes.
  2. Session 1: Selects Rank 1 (Binary Search Trees, takes 90 mins). Fits fully! Remaining capacity: 180 - 90 = 90 mins.
  3. Session 2: Selects Rank 2 (Graph Traversals, needs 120 mins). Available capacity is only 90 mins!
    → Intelligent Topic Splitting: The algorithm allocates the remaining 90 mins to Graphs and stops.
    → Remaining capacity: 90 - 90 = 0 mins.
  4. Result: Rahul's study day is exactly 180 minutes, 100% focused on his most critical exam (DSA), preventing burnout and eliminating decision fatigue!

3. Step-by-Step System Flow & Architecture

Architectural Overview (3-Tier Layered Pattern)

+--------------------------------------------------------------------------+ | PRESENTATION TIER (Angular 21 SPA) | | Dashboard | Daily Schedule | Subjects | Topics | Pomodoro | | +------------------------------------+-------------------------------------+ | HTTP REST / JSON (CORS Port 4200 -> 8080) v +--------------------------------------------------------------------------+ | APPLICATION / CONTROLLER TIER (Spring Boot 3) | | SubjectController | TopicController | ScheduleController | Progress| +------------------------------------+-------------------------------------+ | Java Method Calls / DTO Passing v +--------------------------------------------------------------------------+ | BUSINESS LOGIC TIER (Greedy Optimization Engine) | | ScheduleService (Score Calculation, Sorting, Splitting) | ProgressService| +------------------------------------+-------------------------------------+ | Spring Data JPA Queries v +--------------------------------------------------------------------------+ | PERSISTENCE TIER (Hibernate ORM & Repositories) | | SubjectRepository | TopicRepository | StudySessionRepository | +------------------------------------+-------------------------------------+ | SQL Queries (TCP Port 3306) v +--------------------------------------------------------------------------+ | DATABASE TIER (MySQL 8.0 / H2) | | Table: subjects Table: topics Table: study_sessions | +--------------------------------------------------------------------------+

End-to-End Schedule Generation Lifecycle:

  1. Step 1 (User Action): The student enters 3.0 hours on the Dashboard or Daily Schedule view and clicks "Auto-Generate Schedule".
  2. Step 2 (Frontend Service): Angular's StudySessionService issues an asynchronous HTTP POST request to http://localhost:8080/api/schedule/generate with the JSON payload {"date": "2026-10-16", "availableHours": 3.0}.
  3. Step 3 (CORS & Controller): Spring Boot's CorsConfig permits origin http://localhost:4200. The request enters ScheduleController.generateSchedule().
  4. Step 4 (Deduplication): ScheduleService runs inside an atomic @Transactional boundary. It first invokes studySessionRepository.deleteByScheduledDate(targetDate) to clean any previous plan for that day, preventing duplicate sessions.
  5. Step 5 (Retrieval & Filtering): topicRepository.findByCompletedFalse() retrieves all unstudied topics. Topics whose exam date has already passed are safely filtered out.
  6. Step 6 (Greedy Sorting): The algorithm calculates the multi-factor Priority Score for each topic and sorts the list in descending order ($O(N \log N)$).
  7. Step 7 (Greedy Packing & Splitting): The engine allocates available minutes greedily. When a topic exceeds remaining capacity, it splits the topic to fill the exact remainder.
  8. Step 8 (Database Commit): studySessionRepository.saveAll(plannedSessions) inserts the newly generated sessions into MySQL table study_sessions.
  9. Step 9 (Response & Render): The backend returns HTTP 200 OK with the session list. Angular's reactive template dynamically updates KPI metrics, planned minutes, and the session tracker table.

5. Curated Guide & Viva Questions (With Examiner-Grade Answers)

Q1: Why did you choose a Greedy Algorithm instead of Dynamic Programming (e.g., 0/1 Knapsack)?
Answer: In standard 0/1 Knapsack, an item must either be taken entirely or left out. In study planning, topics can be partially studied or split across study days (Fractional Knapsack property). Greedy algorithms are optimal for fractional packing with a time complexity of $O(N \log N)$ (due to sorting) compared to Dynamic Programming's pseudo-polynomial $O(N \cdot W)$ time complexity. Furthermore, in real life, students benefit from starting a critical topic today even if they can only finish half of it before hitting their daily fatigue limit.
Q2: What is the Time and Space Complexity of your scheduling algorithm?
Answer:
  • Time Complexity: $O(N \log N)$, where $N$ is the number of incomplete topics. Filtering takes $O(N)$, sorting based on the Priority Score takes $O(N \log N)$, and the greedy allocation loop runs in $O(N)$. Hence, the overall time is dominated by the sort step: $O(N \log N)$.
  • Space Complexity: $O(N)$, required to store the filtered list of valid topics and the resulting planned session entities in memory before batch saving.
Q3: How does the application ensure database referential integrity when a Subject is deleted?
Answer: Both in the MySQL foreign key constraint (ON DELETE CASCADE) and in JPA's entity mapping (@OneToMany(mappedBy = "subject", cascade = CascadeType.ALL, orphanRemoval = true)), cascade deletion is enforced. If a course or subject is deleted, all its associated topics and study sessions are automatically pruned, preventing orphan records and database corruption.
Q4: Why did you use Spring Boot 3 instead of traditional Java Spring MVC with WAR deployment?
Answer: Spring Boot 3 provides auto-configuration, opinionated dependency starters, and an embedded Apache Tomcat server. It compiles into a self-contained executable JAR, eliminating the need to install and configure standalone Tomcat servers. It also integrates Jakarta EE 10, Spring 6, and modern Java 17/22 record and pattern matching features.
Q5: What are Angular Standalone Components and why did you use them instead of NgModules?
Answer: Starting from modern Angular, Standalone Components simplify application structure by allowing components to directly declare their dependencies (such as CommonModule, FormsModule, RouterLink) inside their @Component decorator using imports: [...]. This eliminates bulky @NgModule boilerplate, enables better tree-shaking, decreases JavaScript bundle sizes, and makes components independently reusable.
Q6: What is the purpose of Data Transfer Objects (DTOs) in this application?
Answer: DTOs (e.g., ScheduleRequest, DashboardStatsDto, SessionStatusUpdateRequest) decouple the internal database entity models from the external API contract. This protects against security vulnerabilities like over-posting/mass assignment, avoids circular reference issues during Jackson JSON serialization (common with bidirectional JPA relationships), and allows sending tailored, aggregated views (like KPI counts) to the client.
Q7: How does the Pomodoro timer keep running when switching between different Angular routes?
Answer: When timer state was stored inside PomodoroComponent, switching routes triggered Angular's component lifecycle ngOnDestroy(), which destroyed the timer interval. To solve this, timer logic was hoisted into a root-level singleton service (@Injectable({ providedIn: 'root' }) PomodoroService). Because root services persist across router outlets throughout the SPA session, the timer interval continues running uninterrupted in the background.
Q8: How does the system handle CORS (Cross-Origin Resource Sharing)?
Answer: Because the Angular frontend runs on http://localhost:4200 and the Spring Boot backend runs on http://localhost:8080, browsers enforce the Same-Origin Policy. To permit communication, we implemented a global CorsConfig bean implementing WebMvcConfigurer. It explicitly maps /api/** endpoints, allows origin http://localhost:4200, enables HTTP methods (GET, POST, PUT, DELETE, OPTIONS), and allows credentials.
Q9: What happens if a student generates a schedule twice on the same day? Does it duplicate data?
Answer: No. ScheduleService implements an idempotent deduplication mechanism. Before allocating time, it invokes studySessionRepository.deleteByScheduledDate(targetDate) and flushes the persistence context. Any existing study plan for that date is cleanly cleared before fresh sessions are saved, ensuring zero duplicate records.
Q10: How does the application generate audio for the Pomodoro clock without downloading external MP3 files?
Answer: We leveraged the browser's native Web Audio API. When a session completes, a transient AudioContext creates an OscillatorNode emitting a clean sine wave at frequency 587.33 Hz (musical note D5), modulated by a GainNode with an exponential decay curve over 1.2 seconds. This produces an elegant audio notification with 0 KB external asset overhead.
Q11: How would you scale this application to support 100,000 active students simultaneously?
Answer:
  1. Database: Introduce database connection pooling (HikariCP tuning), read-replicas for analytics queries, and composite indexes on (scheduled_date, status) and (subject_id, completed).
  2. Caching: Implement Redis to cache frequent dashboard KPI calculations and subject summaries with time-based TTL invalidation.
  3. Stateless Auth: Add Spring Security with JWT (JSON Web Tokens) to make backend nodes completely stateless for horizontal autoscaling behind an NGINX load balancer.
  4. Async Architecture: Offload heavy weekly analytics batch computations to background worker queues using Spring Batch or RabbitMQ.
Q12: What future enhancements can be added to this project?
Answer:
  • Spaced Repetition (Leitner / SM-2 Algorithm): Integrating spaced intervals for reviewed topics to combat the Ebbinghaus forgetting curve.
  • AI Study Recommendations: Using Large Language Models (LLMs like Gemini) to auto-generate topic breakdown subtasks from uploaded course syllabus PDFs.
  • Mobile Application: Wrapping the Angular client into an Android/iOS app via Capacitor or building a Progressive Web App (PWA) with offline service workers.
